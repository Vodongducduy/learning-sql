Before You Begin

Prerequisites

These examinations assume baseline computer literacy and QA awareness. No prior SQL experience is required for Exams 1–2, but the following foundations will accelerate your progress significantly.

🟢 General Knowledge
  • Understand what a relational database is (tables, rows, columns)
  • Know the difference between a database and a spreadsheet
  • Familiarity with basic data types: text, number, date, boolean
  • Awareness of primary keys and what makes a row unique
  • Can open and use a SQL client (MySQL Workbench, DBeaver, or similar)
🔵 QA Context
  • Know the bug life cycle and software testing fundamentals
  • Understand what an API does and what a response body looks like
  • Familiar with terms: endpoint, payload, status code, response
  • Know what "test data" means and why test cleanup matters
  • Understand data integrity at a conceptual level (correct data in right place)
🟡 Technical Setup
  • MySQL 8.0+ installed locally or access to a practice environment
  • Access to a sample database (e.g. sakila, world, or a QA project DB)
  • Ability to run SQL queries and read results
  • Browser with developer tools for inspecting API responses
🟣 Recommended Experience
  • At least 1 sprint cycle participating in QA activities
  • Attempted to verify at least one API result manually
  • Read or written at least one bug report
  • Reviewed a test case document or test plan

SELECT & Basic Queries
SELECT, FROM, aliases, DISTINCT, ORDER BY, LIMIT, OFFSET, expressions
Fresher 60 Q
▼
📖Required Knowledge
  • SQL statement anatomy: SELECT … FROM … WHERE … ORDER BY … LIMIT
  • The difference between SELECT * and selecting specific columns
  • How column aliases work with AS (and without)
  • What DISTINCT does and when it applies to multiple columns
  • ASC vs DESC sort order; sorting by multiple columns (comma-separated)
  • LIMIT and OFFSET mechanics for pagination (LIMIT count OFFSET skip and LIMIT skip,count syntaxes)
  • SQL arithmetic in SELECT: +, -, *, /, MOD, DIV
  • Scalar functions: UPPER, LOWER, LENGTH, TRIM, CONCAT, ROUND, FLOOR, CEILING, ABS
  • NULL in arithmetic: any expression involving NULL returns NULL
  • SQL comment styles: -- single line and /* block */
⚙️Required Skills
  • Write a valid SELECT for any combination of columns, table, sort, and limit
  • Use aliases to rename columns and tables meaningfully
  • Select the N most recent or top-N records using ORDER BY + LIMIT
  • Write paginated queries using LIMIT + OFFSET
  • Use DISTINCT correctly for single and multi-column deduplication
  • Apply scalar string/math functions inside SELECT
  • Predict what a query returns including NULLs and empty sets
  • Spot and fix common syntax errors (missing column list, wrong clause order)
⚠️Common Traps in This Exam
ORDER BY positionORDER BY 2 sorts by the 2nd SELECT column — valid but confusing. Know what it does.
Alias in WHEREAliases defined in SELECT cannot be used in WHERE (evaluated before SELECT).
LIMIT 10, 20 syntaxLIMIT offset, count — the first number is SKIP, second is COUNT (opposite of what you might expect).
DISTINCT on multiple columnsDISTINCT applies to the entire row combination, not just the first column listed.
NULL arithmeticNULL + 5 = NULL. NULL in any arithmetic expression poisons the whole result.
💡
Study tip: Before this exam, write 20 different SELECT queries against a real database. Practice: selecting specific columns, aliasing, sorting by 2 columns, paginating through results, and applying at least 5 different scalar functions. The questions are practical — syntax you'll write weekly as a QA engineer.
02
🔎
WHERE Clause & Filtering
Comparison operators, BETWEEN, IN, LIKE, IS NULL, AND/OR, operator precedence
Fresher 60 Q
▼
📖Required Knowledge
  • All comparison operators: =, !=, <>, <, >, <=, >=
  • BETWEEN x AND y is inclusive on both ends
  • IN (list) and NOT IN (list) — how they work with literals and subqueries
  • LIKE wildcards: % (zero or more chars) and _ (exactly one char)
  • IS NULL and IS NOT NULL — why = NULL never works
  • Logical operators AND, OR, NOT and their precedence (AND before OR)
  • NULL in comparisons: NULL = NULL → NULL (not TRUE)
  • NOT IN with NULL in the list silently returns empty results
  • REGEXP for pattern matching beyond LIKE
  • Case sensitivity in string comparisons (collation-dependent)
⚙️Required Skills
  • Write WHERE clauses that correctly filter on equality, ranges, lists, and patterns
  • Use IS NULL / IS NOT NULL correctly (never = NULL)
  • Build compound conditions with AND, OR, NOT — including parentheses for precedence
  • Write LIKE patterns for starts-with, ends-with, contains, and exact-length matches
  • Detect and fix the NOT IN + NULL trap using NOT EXISTS instead
  • Filter records by date ranges using INTERVAL syntax
  • Write QA-relevant filters: detect empty fields, invalid formats, test data patterns
⚠️Common Traps in This Exam
WHERE col = NULLThis never matches anything. Always use IS NULL. This is the single most common fresher SQL mistake.
NOT IN with NULLsNOT IN (1, 2, NULL) returns zero rows for any value — NULL poisons the entire NOT IN evaluation.
AND vs OR precedencea=1 OR b=2 AND c=3 means a=1 OR (b=2 AND c=3). Use parentheses to make intent explicit.
LIKE '%value' performanceLeading wildcard prevents index use — full table scan. Know the performance implication even if the question doesn't ask about it.
BETWEEN inclusivityBETWEEN 18 AND 65 includes both 18 and 65. Many candidates assume exclusivity.
💡
Study tip: Open any table and practice filtering: find records created in the last 7 days, find rows with empty or NULL emails, find all active users whose name starts with 'A' and ends with 'n'. For each query, predict the result before running. The NULL trap questions are high-value — study IS NULL vs = NULL until it's reflexive.
03
🔗
JOIN Operations
INNER, LEFT, RIGHT, FULL OUTER, SELF, CROSS JOIN — anti-joins, fanout, integrity checks
Fresher→Junior 60 Q
▼
📖Required Knowledge
  • INNER JOIN: only rows with matches in both tables
  • LEFT JOIN: all left rows + NULLs for unmatched right rows
  • RIGHT JOIN: all right rows + NULLs for unmatched left rows
  • FULL OUTER JOIN concept (simulate in MySQL with LEFT UNION RIGHT)
  • CROSS JOIN: Cartesian product (m × n rows)
  • SELF JOIN: joining a table to itself using aliases
  • ON clause vs USING clause; ON vs WHERE for LEFT JOIN filtering
  • Anti-join pattern: LEFT JOIN + WHERE right.id IS NULL
  • JOIN vs subquery for existence checks
  • Fanout: one-to-many join duplicates left rows
  • Referential integrity checking with LEFT JOIN + IS NULL
⚙️Required Skills
  • Choose the correct JOIN type for a given requirement
  • Write a LEFT JOIN that finds all records including unmatched ones
  • Write an anti-join to detect orphan records
  • Join three or more tables in a single query
  • Use table aliases correctly in complex JOIN queries
  • Recognise and avoid accidental CROSS JOIN (missing ON clause)
  • Check referential integrity between parent and child tables
  • Explain why WHERE on a right-table column converts LEFT JOIN to INNER JOIN
  • Use DISTINCT to remove fanout duplicates
⚠️Common Traps in This Exam
WHERE converts LEFT JOINAdding WHERE right.col = 'x' to a LEFT JOIN eliminates unmatched rows — effectively making it INNER JOIN.
NULL join keysNULL = NULL in a JOIN condition returns NULL (not TRUE). NULL-keyed rows never match.
Fanout in aggregatesSUM after joining one-to-many inflates results. Aggregate BEFORE joining or use DISTINCT.
ON vs USINGUSING (col) only works if both tables have identically named columns. Wrong usage of USING produces semantic errors.
SELECT * on JOINReturns duplicate column names (e.g., 'id' from both tables). Always name your columns in JOIN queries.
💡
Study tip: Draw the Venn diagram for INNER, LEFT, and RIGHT JOIN before writing any code. Practice the anti-join pattern specifically — LEFT JOIN … WHERE right.id IS NULL — as it appears in nearly every QA integrity check scenario. Write a query that finds orphan records in your test database.
04
📊
Aggregation & GROUP BY
COUNT, SUM, AVG, MIN, MAX, GROUP BY, HAVING, conditional aggregation
Fresher→Junior 60 Q
▼
📖Required Knowledge
  • COUNT(*) vs COUNT(col) — COUNT(*) includes NULLs; COUNT(col) doesn't
  • SUM, AVG, MIN, MAX all ignore NULL values
  • GROUP BY groups rows with identical values; SELECT columns must be grouped or aggregated
  • HAVING filters groups after aggregation (WHERE filters rows before)
  • COUNT(DISTINCT col) counts unique non-NULL values
  • Aggregate functions return NULL for empty sets (except COUNT which returns 0)
  • GROUP BY on expressions: YEAR(date), DATE_FORMAT, LENGTH etc.
  • GROUP_CONCAT for concatenating grouped values
  • WITH ROLLUP for subtotals and grand totals
  • Conditional aggregation: SUM(CASE WHEN … THEN 1 ELSE 0 END)
⚙️Required Skills
  • Write GROUP BY queries that count, sum, or average per category
  • Use HAVING to filter groups on aggregate values
  • Detect duplicates using GROUP BY + HAVING COUNT > 1
  • Write daily/monthly time-series aggregations
  • Count items meeting a condition within a group (conditional SUM/CASE)
  • Build test-result summary queries: pass rate, fail count, total per suite
  • Find the top-N category by count or sum
  • Explain why aggregate functions cannot appear in WHERE
⚠️Common Traps in This Exam
Non-aggregated SELECT columnSELECT dept, name, COUNT(*) without name in GROUP BY — invalid or non-deterministic. All SELECT columns must be grouped or aggregated.
WHERE on aggregateWHERE COUNT(*) > 5 is invalid. Aggregates are not computed at WHERE time. Use HAVING.
COUNT(*) vs SUM for empty setCOUNT(*) returns 0 for an empty set; SUM returns NULL. Wrap SUM in COALESCE(SUM(...), 0).
Fanout inflates SUMJoining before aggregating in a one-to-many relationship inflates SUM results. Aggregate first, join second.
💡
Study tip: Write a complete test-results reporting query from scratch: count tests by suite, calculate pass rates, filter to suites with failures only. This one exercise covers GROUP BY, HAVING, conditional aggregation, and COALESCE. The duplicate-detection pattern (GROUP BY + HAVING COUNT > 1) is a guaranteed exam topic — practise it on every table you can find.
05
🪆
Subqueries & IN / EXISTS
Scalar, correlated, derived tables, CTEs, IN vs EXISTS, NOT IN NULL trap, ANY/ALL
Junior 60 Q
▼
📖Required Knowledge
  • Types: scalar (one value), row, column, table (multi-row multi-col)
  • Correlated subquery: references outer query column; runs per outer row
  • Uncorrelated subquery: independent; runs once
  • Derived table: subquery in FROM clause, must have alias
  • CTE (WITH clause): named, reusable, defined before main query
  • Recursive CTE: base case UNION ALL recursive case for hierarchical data
  • IN vs = ANY (identical); NOT IN vs <> ALL (identical but NULL-unsafe)
  • EXISTS: Boolean — returns TRUE if subquery has any rows
  • NOT EXISTS is NULL-safe; NOT IN is not
  • Scalar subquery returning 0 rows = NULL; 2+ rows = error
⚙️Required Skills
  • Write a scalar subquery to compare a value against an aggregate (e.g. above average)
  • Write an IN subquery to filter based on another table's values
  • Write NOT EXISTS to safely find records with no matching child
  • Build a derived table (subquery in FROM) with an alias
  • Refactor nested subqueries into readable CTEs
  • Explain when a correlated subquery is a performance risk and how to rewrite it
  • Use EXISTS for existence checks in QA verification queries
⚠️Common Traps in This Exam
NOT IN + NULL = empty resultNOT IN(SELECT col …) returns no rows if col has any NULL. Always use NOT EXISTS for nullable subquery columns.
Scalar subquery returns 2+ rowsA scalar subquery used in WHERE or SELECT must return exactly one row. Multiple rows cause a runtime error.
Correlated subquery performanceRuns once per outer row. On a 100k-row table = 100k executions. Replace with JOIN or window function where possible.
IN vs EXISTS semanticsIN compares values; EXISTS checks row existence. For large subquery results, EXISTS short-circuits at first match — generally faster.
💡
Study tip: Memorise the NOT IN / NOT EXISTS difference — it will appear in the exam and is a real production bug source. Practise rewriting a correlated subquery as a JOIN and a nested subquery as a CTE. Understanding when to use each pattern (not just syntax) is what this exam tests.
06
🚫
NULL Handling & Data Integrity
NULL semantics, COALESCE, NULLIF, three-valued logic, constraints, integrity checks
Junior 60 Q
▼
📖Required Knowledge
  • NULL = unknown/missing — NOT zero, NOT empty string, NOT false
  • Three-valued logic: TRUE, FALSE, NULL — and its truth tables for AND, OR, NOT
  • NULL in arithmetic always yields NULL (NULL propagation)
  • COALESCE(a, b, c): first non-NULL argument
  • NULLIF(a, b): returns NULL if a = b, else returns a
  • IFNULL(a, b): MySQL-specific 2-arg version of COALESCE
  • NULL-safe equality operator <=> (spaceship)
  • Constraints: NOT NULL, UNIQUE (allows multiple NULLs in MySQL), PRIMARY KEY, FOREIGN KEY, CHECK
  • Referential integrity: FK must reference existing PK or be NULL
  • NULL in aggregate functions: all except COUNT(*) ignore NULL
⚙️Required Skills
  • Use COALESCE to replace NULL with a safe default in reports and calculations
  • Use NULLIF to prevent division-by-zero errors
  • Write queries that correctly detect NULL, empty string, and whitespace-only values
  • Apply three-valued logic to predict query results involving NULL
  • Write QA integrity checks that find: NULL required fields, orphan records, duplicate keys
  • Explain the QA implications of each constraint type (NOT NULL, UNIQUE, FK)
  • Detect data integrity violations across multiple tables using JOIN patterns
⚠️Common Traps in This Exam
NULL ≠ 0 ≠ ''Each represents a different semantic state. NULL = unknown, 0 = zero, '' = empty known value. They compare and store differently.
NULL AND/OR logicNULL AND TRUE = NULL. NULL OR FALSE = NULL. NULL OR TRUE = TRUE. Memorise the truth table.
UNIQUE allows multiple NULLsIn MySQL, a UNIQUE column can have multiple NULL rows because NULL != NULL.
IN (NULL, '') doesn't find NULLsIN uses = internally. NULL = NULL → NULL, not TRUE. Use IS NULL separately.
SUM of empty set = NULLNot 0. Always COALESCE(SUM(...), 0) in financial or count-based calculations.
💡
Study tip: Draw the three-valued logic truth table and memorise it — this exam heavily tests NULL logical reasoning. Practise writing COALESCE(SUM(amount), 0) and price / NULLIF(qty, 0) until they feel natural. Run integrity checks on a real database and document what you find.

📅
Date & Time Functions
NOW, CURDATE, DATE_ADD, DATEDIFF, DATE_FORMAT, TIMESTAMP, timezone handling
Junior 60 Q
▼
📖Required Knowledge
  • NOW() → datetime; CURDATE() → date only; CURTIME() → time only
  • DATE_ADD(date, INTERVAL n unit) and DATE_SUB; valid units: SECOND, MINUTE, HOUR, DAY, WEEK, MONTH, YEAR
  • DATEDIFF(d1, d2): days as integer (d1 − d2)
  • TIMESTAMPDIFF(unit, start, end): difference in any unit
  • Extraction: YEAR, MONTH, DAY, HOUR, MINUTE, SECOND, DAYNAME, DAYOFWEEK, WEEKDAY, QUARTER
  • DATE_FORMAT(date, format_string) — format codes: %Y %m %d %H %i %s %W %M
  • STR_TO_DATE for parsing string dates
  • DATETIME vs TIMESTAMP: range, timezone behaviour, 2038 problem
  • LAST_DAY, MAKEDATE, PERIOD_DIFF, PERIOD_ADD
  • Using DATE() to strip time component for date-only comparison
⚙️Required Skills
  • Query records created today, in the last N days/hours/minutes
  • Calculate the difference between two dates in days, hours, or minutes
  • Group records by day, week, month, or year for time-series reports
  • Format dates for display using DATE_FORMAT
  • Find records from a specific month, quarter, or year
  • Verify SLA compliance using DATEDIFF or TIMESTAMPDIFF
  • Handle DATETIME vs DATE comparison pitfalls (time component truncation)
  • Choose DATETIME vs TIMESTAMP for different storage requirements
⚠️Common Traps in This Exam
BETWEEN with DATETIMEBETWEEN '2024-01-01' AND '2024-01-31' misses records on Jan 31 after midnight. Use < '2024-02-01' instead.
NOW() - 7 subtracts secondsNOW() - 7 subtracts 7 seconds, not 7 days. Always use INTERVAL: NOW() - INTERVAL 7 DAY.
MONTH() groups cross-yearGROUP BY MONTH(date) groups January across all years together. Use DATE_FORMAT(date,'%Y-%m') for year-aware grouping.
2038 TIMESTAMP problemTIMESTAMP overflows in 2038. Use DATETIME for dates that may extend beyond that.
💡
Study tip: Practice date range queries daily. Write one query each morning: find yesterday's records, find records from this week, find records more than 30 days old. Verify SLAs by computing DATEDIFF between created_at and resolved_at on a real bugs table. These are the exact queries you'll write in QA sprints.

QA Data Verification Patterns
API result verification, test data cleanup, integrity checks, state machine validation
Junior 60 Q
▼
📖Required Knowledge
  • POST → INSERT verification: find the created record by unique identifier
  • PUT/PATCH → UPDATE verification: select specific updated fields and compare
  • DELETE verification: COUNT should return 0 for the deleted ID
  • Bulk operation verification: count before and after, compare delta
  • Duplicate detection patterns (GROUP BY + HAVING)
  • Referential integrity checks (LEFT JOIN + WHERE IS NULL)
  • State machine validation: detect invalid status transitions
  • Soft-delete verification: row exists, deleted_at is set
  • Test data cleanup strategies: time-window + marker patterns
  • Idempotency verification: same result after N calls
⚙️Required Skills
  • Write a DB verification query for any CRUD API call
  • Detect data quality issues: NULL required fields, orphans, duplicates, status mismatches
  • Verify calculated fields (e.g. discounted price, total = sum of items)
  • Confirm cascade operations (CASCADE DELETE, related table updates)
  • Write safe test data cleanup queries with correct WHERE conditions
  • Verify audit log entries were created correctly
  • Detect test data pollution in production-like environments
  • Write production-safe verification queries (LIMIT, read-only, specific WHERE)
⚠️Common Traps in This Exam
SELECT * for verificationToo broad — schema changes silently add columns and break comparisons. Select specific fields that the API actually returns.
No WHERE on cleanup DELETEDELETE FROM table without WHERE deletes everything. Always combine data marker AND time window in cleanup queries.
Trust the API countAPI-reported counts (total_count in pagination) may differ from actual DB count. Always verify with a direct COUNT(*) query.
Missing float toleranceComparing float calculations with = fails due to precision. Use ABS(calculated - stored) < 0.01 for financial values.
💡
Study tip: This is the most practically important exam. After every API test you run, write a SQL query to verify the database state. Build a personal library of 10–15 "template" verification queries you can adapt quickly. The exam simulates real QA scenarios — your SQL must be both correct and safe to run on shared environments.

Advanced SQL
CASE expressions, UNION, Window Functions (ROW_NUMBER, RANK, LAG, LEAD, SUM OVER), CTEs, string/numeric functions
Junior+ 60 Q
▼
📖Required Knowledge
  • CASE WHEN … THEN … ELSE … END — evaluated top-to-bottom, first match wins
  • CASE inside aggregates (conditional SUM/COUNT)
  • UNION (deduplicate) vs UNION ALL (keep all rows) — column count and type requirements
  • Window function syntax: function() OVER (PARTITION BY … ORDER BY …)
  • ROW_NUMBER: always unique; RANK: gaps for ties; DENSE_RANK: no gaps
  • LAG(col, n) and LEAD(col, n): access previous/next row values
  • SUM/AVG OVER with ORDER BY creates running totals
  • NTILE(n): distributes rows into n equal buckets
  • Window frames: ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
  • FIRST_VALUE, LAST_VALUE, PERCENT_RANK, CUME_DIST
  • String functions: CONCAT_WS, SUBSTRING_INDEX, LOCATE, LPAD, REPLACE, REGEXP_REPLACE
  • Numeric: TRUNCATE (no rounding), FORMAT (thousands separator), SIGN, GREATEST, LEAST
⚙️Required Skills
  • Write CASE expressions for categorisation and conditional output
  • Use CASE inside aggregates to count/sum by condition (pivot pattern)
  • Choose UNION vs UNION ALL for correct deduplication behaviour
  • Use ROW_NUMBER to deduplicate and get latest-per-group
  • Choose between ROW_NUMBER, RANK, DENSE_RANK based on tie-handling needs
  • Use LAG and LEAD for trend detection and regression analysis
  • Build a running total using SUM OVER with ORDER BY
  • Construct a recursive CTE for hierarchical data
  • Pivot a table using conditional aggregation (CASE + GROUP BY)
⚠️Common Traps in This Exam
RANK vs DENSE_RANK tiesRANK skips numbers after ties (1,1,3). DENSE_RANK doesn't (1,1,2). Know which is needed for leaderboards vs fair rankings.
PARTITION BY doesn't filterPARTITION BY groups for window calculation — it does NOT remove rows from the result. Use WHERE/HAVING to filter rows.
LAST_VALUE frame issueLAST_VALUE requires ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING to work correctly — default frame stops at current row.
UNION column requirementsBoth SELECT statements must have the same number of columns and compatible types, or UNION throws an error.
TRUNCATE vs ROUNDTRUNCATE(3.9, 0) = 3 (no rounding). ROUND(3.9, 0) = 4. They are not interchangeable.
💡
Study tip: Window functions are the hardest topic in this series — dedicate at least 3 study sessions to them alone. Start with ROW_NUMBER for deduplication, then learn RANK/DENSE_RANK for leaderboards, then LAG/LEAD for trend detection. The "top N per group" pattern using ROW_NUMBER in a subquery is the most frequently tested window function use case.

Comprehensive Mixed Review
All topics combined — multi-step reasoning, real QA scenarios, query design decisions
All Levels 60 Q
▼
📖Required Knowledge
  • All topics from Exams 1–9 are in scope — this is a full review
  • Logical query writing: SELECT the right thing, from the right table, with the right condition
  • Selecting the correct SQL technique for a given problem (JOIN vs subquery vs window function)
  • Multi-table data scenarios: order + payment + user + product

  • QA-specific scenarios: API verification, cleanup, integrity, audit

⚙️Required Skills
  • Analyse a QA scenario and write the correct SQL to verify it
  • Choose the most appropriate SQL technique among multiple valid options
  • Detect anti-patterns and explain why they're wrong (SELECT *, = NULL, WHERE aggregate)

  • Understand query execution order and its implications for filtering and aliasing
⚠️Common Traps in This Exam
Technique selectionChoosing JOIN when EXISTS is faster, or correlated subquery when a window function is cleaner. Know when to use each.
Clause order errorsThis exam combines multiple concepts — getting the order of SELECT/FROM/WHERE/GROUP BY/HAVING/ORDER BY wrong causes syntax errors.
NULL in complex queriesNULL propagation across JOINs, aggregates, and CASE expressions produces surprising results. Trace NULL through each operation step by step.
Ignoring readabilityA correct but unreadable query is a QA liability. Readable SQL uses aliases, line breaks, and comments — and this exam rewards that understanding.
💡
Study tip: Treat this exam as a simulation of your real QA work. Take the exam after a 1-week break from active studying — if you need to look things up to pass, your foundations aren't solid enough yet. The best preparation is writing real SQL daily on real data, not just practising quizzes.
